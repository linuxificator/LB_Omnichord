# Codex context rebuild - extraction scope

This file defines the required level of detail for the Codex knowledge base. Previous summaries were insufficient. The target is not a README but a project memory database.

## Required documentation granularity

Every historical decision must be recorded as:

- Context: why the discussion started.
- Problem: what was observed.
- Options considered.
- Decision made.
- Reason for decision.
- Consequences.
- Forbidden future changes.
- Verification/test procedure.

## GUI information that must be captured

The GUI documentation must not only describe components. It must capture exact behavior:

- widget placement;
- visual states;
- colors and assets;
- touch behavior;
- mouse behavior;
- press/release behavior;
- long press behavior;
- interaction between chord selection, accompaniment, strum and rhythm;
- what continues running when another control changes;
- what resets and what does not reset.

## Music behavior information that must be captured

The documentation must explicitly describe:

- chord activity levels;
- sustained chord behavior;
- long press semantics;
- accompaniment lifecycle;
- rhythm lifecycle;
- rhythm independence from chord changes;
- strum generation;
- bass behavior;
- patch changes while playing;
- AMY wire commands generated by UI actions.

## Failure archive requirements

Each failure entry must contain:

- symptom;
- reproduction steps;
- incorrect hypotheses considered;
- root cause;
- actual fix;
- regression test.

Examples of categories to include:

- Qt strum not producing sound while chords worked.
- Accidental AMY embedding attempts in frontend.
- Android/Godot lifecycle coupling mistakes.
- Audio latency and DMA experiments.
- ESP32-P4 render loop timing issues.

## Source material

Primary source is the ChatGPT export containing the project discussions. Repository documentation and source code are secondary sources. Conflicts must be documented, not silently resolved.
